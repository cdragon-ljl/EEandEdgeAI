# 技术文章编辑规范

本站技术文章的第一目标是让读者沿一条连续路径建立可用于读源码和解决工程问题的模型。自动测试只能防止明显退化，不能代替技术审读。

## 一、学习路径

每篇文章按需要组织以下环节，不使用固定模板强行凑齐：

1. 说明技术要解决的问题，以及缺少该机制时会遇到的限制。
2. 定义参与对象、术语、协议字段、硬件状态和软件数据结构。
3. 沿一次真实请求、状态转换或数据路径解释工作过程。
4. 映射到 Linux/协议栈对象、源码入口和资源所有权变化。
5. 给出可以观察的证据、实验方法、错误分层和工程取舍。

新术语必须在首次依赖前定义。文章不能假设初学者已经理解缩写，也不能在基础模型建立前直接讨论 API。

## 二、章节规则

- 二级章节只承载文章主问题的一个完整阶段。
- 三级章节只用于能够独立展开多个自然段的子问题。
- 一两句话、一个术语或一个故障现象使用段内加粗、表格或列表，不单独建章。
- 标题数量和字符数量不是质量指标；需要多少章节由推导路径决定。
- 小结只归纳正文已经证明的结论，不追加新知识点。

## 三、技术深度

- 协议字段必须说明产生者、消费者、单位、取值和对行为的影响。
- 数据结构必须说明创建、发布、并发访问、停止和释放阶段。
- API 必须说明调用前置条件、改变的状态、失败结果和回滚关系。
- 异步数据路径必须明确 CPU、驱动、控制器和设备之间的 buffer 所有权。
- 性能分析必须建立分层模型，并同时考虑吞吐、延迟、CPU、内存和错误恢复。
- 不虚构 benchmark、调用链、寄存器语义或不同硬件上的统一行为。

## 四、图示规则

以下信息仅靠文字不易形成模型时必须作图：

- 架构、拓扑、硬件连接和软件栈使用结构图。
- 枚举、控制请求、初始化和错误恢复使用时序图。
- 链路训练、生命周期、reset 和 queue ownership 使用状态图。
- URB、DMA、descriptor ring 和多队列使用数据流图。
- 跨层排错使用决策树或证据链图。

图放在相关机制首次展开的位置。正文必须解释节点、箭头和关键转折，禁止把图集中堆到文末或为了数量添加装饰图。

## 五、资料来源

技术结论优先核对 USB-IF、PCI-SIG 公共资料、Linux 内核文档和源码、CherryUSB 官方 tag。每篇主线文章至少列出两项实际使用的一手资料。

引用源码时区分稳定概念和版本实现；引用厂商控制器时明确哪些行为来自具体 IP，而不是总线规范。

## 六、发布验收

发布前逐篇确认：

- 初学者能理解开头定义、学习动机和本文边界。
- 协议、硬件、Linux 对象和源码调用链相互对应。
- 代码包含所有权、并发、错误回滚和可验证结果。
- 需要架构、时序、状态或所有权图的地方已经作图并被正文解释。
- 读完后可以完成一个实验、读懂一段源码或定位一类故障。
- Mermaid、代码块、链接、Astro 构建和 GitHub Pages 渲染均通过验证。
