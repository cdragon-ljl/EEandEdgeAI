前面的链路里，画面已经是干净的 YUV 帧了。但一帧 1080p NV12 是 3.1MB，30fps 就是 93MB/s——这个量级网络传不动、存储放不下。编码器（H.264/H.265）能把码率压到 1/50~1/100，画质肉眼看不出差别。这一篇把编码原理讲透：**为什么能压、怎么压、I/P/B 帧与 GOP、码率控制、H.264 vs H.265、Profile/Level**，并用 FFmpeg 做实验验证每个概念。

**双轨对照**：PC 端 FFmpeg 反复编码对比（不同 GOP/码率/编码器），板端后面接 VENC 硬编时用同一套参数概念。

## 一、为什么需要编码：数据量是天文数字

先算一笔账：

```
1080p 一帧 NV12 = 1920 × 1080 × 1.5 字节 = 3,110,400 B ≈ 3.0 MB
30fps 一秒     = 3.0 MB × 30           ≈ 89 MB/s
一小时         ≈ 313 GB
一张 32GB 卡   只能存 6 分钟
```

**定义**：视频编码 = 用算法消除视频数据的冗余，把码率降下来，解码端再还原。

**类比**：一本 1000 页的书，如果每页都从第一个字抄到最后一个字，体积巨大；但如果只写"第 2 页和第 1 页只有 3 个字不同"，体积就小了——视频编码就是干这个的：**不重复存相同的信息**。

**三大冗余**：

| 冗余 | 含义 | 例子 | 编码手段 |
|:---|:---|:---|:---|
| 空间冗余 | 同一帧内相邻像素相似 | 天空、墙面、桌面 | 帧内预测 + 变换量化 |
| 时间冗余 | 相邻帧内容高度相似 | 静止背景、缓慢移动 | 帧间预测（运动补偿） |
| 视觉冗余 | 人眼不敏感的信息 | 高频细节、颜色细节 | 量化（丢不敏感信息） |

**编码器的本质**：把这三类冗余尽可能榨干，只留下"必要的信息"。

## 二、帧内编码：消灭空间冗余

### 2.1 分块处理

**定义**：编码器不直接处理整帧，而是把帧分成小块。H.264 的基本块是 **16×16 宏块（Macroblock）**；H.265 是 **CTU（Coding Tree Unit）**，最大 64×64，可递归细分。

**类比**：把大画布切成很多小格子，一格一格地处理——分块让"局部相似性"能被利用（天空那一块整个都是蓝的，可以非常高效地表示）。

### 2.2 帧内预测

**原理**：用**相邻已编码像素**预测当前块的内容。因为相邻像素高度相关，预测值往往很接近真实值——**只编码"预测与实际"的差值（残差）**，残差通常很小，压缩率大增。

**H.264 亮度有 9 种预测方向**（水平/垂直/对角…），H.265 有 35 种——预测方向越多，越能贴近真实纹理，残差越小。

```mermaid
flowchart LR
    A["原始块"] --> B["选择最佳预测方向<br/>用左/上已编码像素"] --> C["残差<br/>原始 - 预测"]
    C --> D["变换 + 量化"] --> E["熵编码"] --> F["码流"]
    B --> D
```

### 2.3 变换、量化、熵编码

- **变换（Transform）**：把残差从像素域转到频域（DCT 类）。自然图像的残差能量集中在低频——变换后多数系数接近 0，**只保留少量大系数**；
- **量化（Quantize）**：把系数除以量化步长取整。**这是主要的有损环节**——步长越大，细节丢得越多，码率越低，画质越差；
- **熵编码（Entropy Coding）**：对量化后的系数做无损压缩（H.264 的 CAVLC/CABAC），把统计冗余也榨干。

**量化与画质的关系**：量化步长 = 压缩率旋钮。步长小 → 细节保留多 → 码率高；步长大 → 细节丢弃 → 出现"块效应"（马赛克）。

**类比**：残差像"改作业只标出差的地方"；量化像"只保留到小数点后一位"——代价是丢掉的信息补不回来。

## 三、帧间编码：消灭时间冗余

### 3.1 运动估计与运动补偿

**核心观察**：相邻两帧之间，除了画面边缘的微小变化，**绝大多数内容只是"平移"了**（人或镜头在动）。与其编码整个新帧，不如说"上一帧的这个块，移动了 (dx, dy)"。

- **运动估计（ME）**：在当前帧里找块，去参考帧里搜索最匹配的位置，得到**运动矢量（MV）**；
- **运动补偿（MC）**：解码端按 MV 把参考帧的块"搬"过来，加上残差，恢复当前块。

**关键点**：运动估计是编码器**最耗算力的部分**（搜索范围大），也是硬件编码器（VENC）的价值所在——硬件做运动搜索又快又省。

【图1：帧间预测——运动补偿示意】

```mermaid
flowchart LR
    A["参考帧（上一帧）"] --> B["运动估计<br/>搜索最匹配块"] --> C["运动矢量 MV=(dx,dy)"]
    B --> D["运动补偿<br/>按 MV 搬块"] --> E["预测块"]
    E --> F["残差 = 当前块 - 预测块"] --> G["变换量化熵编码"] --> H["码流"]
```

### 3.2 帧类型：I / P / B

| 帧类型 | 全称 | 编码方式 | 压缩率 | 特点 |
|:---|:---|:---|:---|:---|
| I 帧 | Intra frame | 完整帧内编码 | 最低 | 可独立解码；**随机访问点** |
| P 帧 | Predictive frame | 参考前面的帧 | 中 | 依赖前帧 |
| B 帧 | Bi-directional frame | 参考前后两帧 | 最高 | 依赖前后帧，**解码延迟高** |

**为什么 B 帧压缩率最高**：B 帧可以同时参考前面和后面的帧——中间帧通常和前后都相似，取两者平均预测更准，残差更小。代价：**解码 B 帧要等后面的帧先到**（重排序），延迟增加。

**工程选择**：
- **低延迟场景（对讲/直播）**：不用 B 帧（或极少），避免重排序延迟；
- **存储/点播**：用 B 帧省码率。

### 3.3 GOP（Group of Pictures）

**定义**：GOP = 一组帧，从 I 帧开始到下一个 I 帧前结束。格式如：`I P P P P B P B ... I`。

【图2：GOP 结构】

```mermaid
flowchart LR
    I1["I"] --> P1["P"] --> P2["P"] --> B1["B"] --> P3["P"] --> B2["B"] --> I2["I"]
```

**GOP 的权衡**：
- **GOP 大（I 帧少）**：码率低（I 帧最贵）——但错误恢复慢、随机访问难（要从最近的 I 帧开始解码）；
- **GOP 小（I 帧多）**：码率高——但丢包后很快能恢复（新 I 帧刷新）、拖动快。

**工程建议**：
- 监控/直播：GOP 2~4 秒（错误恢复快）；
- 存储：GOP 可长（省码率）；
- **I 帧间隔必须是整数秒**（如 30fps 时 GOP=60 是 2 秒），否则关键帧时间点不整齐，播放器"快进/seek"体验差。

**I 帧有多贵**：I 帧大小通常是 P 帧的 5~20 倍（完整帧内编码 vs 只存运动矢量+残差）。

## 四、H.264 vs H.265：差在哪

**定义**：H.265（HEVC）是 H.264（AVC）的继任者，目标是**同画质码率减半**。

| 维度 | H.264 | H.265 |
|:---|:---|:---|
| 最大块 | 16×16 宏块 | 64×64 CTU（递归分块） |
| 帧内预测方向 | 9 种（亮度） | 35 种 |
| 运动补偿 | 1/4 像素精度 | 1/4 像素 + 更优插值 |
| 变换单元 | 4×4 / 8×8 | 最大 32×32 |
| 熵编码 | CAVLC/CABAC | CABAC 增强 |
| 同质量码率 | 基准 | **约省 50%** |

**工程含义**：
- **4K 视频 H.265 优势明显**（大块 CTU 对高分辨率更有效）；
- H.265 **编码/解码算力要求更高**（块递归搜索更复杂）、专利授权更复杂；
- 嵌入式选型：RV1126 硬件编码器 **H.264/H.265 都支持**——4K30 用 H.265 省码率，1080p 用 H.264 兼容性最好（老播放器/浏览器对 H.264 支持最全）。

## 五、Profile 与 Level：兼容性参数

**定义**：
- **Profile（档次）**：规定编码特性集合——H.264 的 **Baseline**（无 B 帧，低算力，早期视频通话）、**Main**（有 B 帧）、**High**（高保真，8×8 变换）；
- **Level（级别）**：规定分辨率/帧率/码率上限——如 **Level 4.0** ≈ 1080p30，**Level 4.2** ≈ 1080p60，**Level 5.1** ≈ 4K30。

**工程含义**：
- **解码端能力必须 ≥ 编码端**：编码用 High@L4.2，解码端必须支持 High 和 L4.2，否则播放不了；
- **老设备兼容性**：老盒子/老电视可能只支持 Baseline@L3.x——面向兼容性时降低 profile/level；
- 查兼容性：`ffprobe` 看流的 profile/level，或看设备说明书。

## 六、码率控制：CBR / VBR / CRF

**定义**：码率控制决定"每个 GOP/帧分多少码率"。核心矛盾：**码率低省带宽，画质差；码率高画质好，费带宽**。

| 模式 | 行为 | 适用 | 特点 |
|:---|:---|:---|:---|
| CBR | 固定码率，画面复杂时牺牲质量 | 监控/推流 | 带宽恒定，网络稳定 |
| VBR | 可变码率，复杂画面给更多码率 | 存储 | 相同平均码率画质更好 |
| CRF（FFmpeg） | 固定质量，码率随内容浮动 | 离线转码 | 一次设置，质量恒定 |

**码率档位经验值**（1080p30 H.264，具体以实测为准）：

| 码率 | 质量 | 场景 |
|:---|:---|:---|
| 1 Mbps | 较差（复杂画面有块效应） | 极限省带宽 |
| 2~4 Mbps | 良好 | 监控/对讲主流 |
| 6+ Mbps | 优秀 | 高要求存储 |

**码率、分辨率、帧率、质量的关系**：分辨率↑ 需要码率↑；帧率↑ 需要码率↑；固定码率下，画面越复杂（运动多/纹理密）画质越差——这就是为什么监控画面静止时清晰、有人走动时变糊。

## 七、实操：FFmpeg 验证每个概念

### 7.1 生成测试源

```bash
# 生成 5 秒测试视频（含运动：testsrc2 有滚动元素）
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -t 5 -c:v libx264 -preset veryfast test_src.mp4
```

### 7.2 看帧类型与大小

```bash
# GOP=30（每 30 帧一个 I 帧），编码后逐帧看类型和字节数
ffmpeg -i test_src.mp4 -c:v libx264 -g 30 -bf 2 -fps_mode passthrough g30.mp4
ffprobe -select_streams v -show_frames -show_entries frame=pict_type,pkt_size g30.mp4 \
  | grep -E "pict_type|pkt_size" | head -60
```

**观察**：I 帧 `pkt_size` 远大于 P/B 帧；B 帧最小。**这是"I 帧最贵"的直接证据**。

### 7.3 GOP 长短对比

```bash
ffmpeg -i test_src.mp4 -c:v libx264 -g 15 out_g15.mp4   # I 帧多
ffmpeg -i test_src.mp4 -c:v libx264 -g 120 out_g120.mp4 # I 帧少
ls -lh out_g15.mp4 out_g120.mp4          # 对比大小
ffprobe -v error -select_streams v -show_entries stream=bit_rate out_g15.mp4
ffprobe -v error -select_streams v -show_entries stream=bit_rate out_g120.mp4
```

**预期**：GOP=15 的码率明显更高（I 帧占比大）。

### 7.4 码率控制对比

```bash
# CBR 固定 1Mbps
ffmpeg -i test_src.mp4 -c:v libx264 -b:v 1M -maxrate 1M -bufsize 2M out_cbr.mp4
# CRF 固定质量（23 中等，35 较差）
ffmpeg -i test_src.mp4 -c:v libx264 -crf 23 out_crf23.mp4
ffmpeg -i test_src.mp4 -c:v libx264 -crf 35 out_crf35.mp4
ls -lh out_cbr.mp4 out_crf23.mp4 out_crf35.mp4
# 截帧对比画质
ffmpeg -i out_crf23.mp4 -vf "select=eq(n\,60)" -vframes 1 f23.png
ffmpeg -i out_crf35.mp4 -vf "select=eq(n\,60)" -vframes 1 f35.png
```

**观察**：CRF 35 的文件小但块效应明显；CRF 23 是"质量优先"。

### 7.5 H.264 vs H.265 同质量对比

```bash
ffmpeg -i test_src.mp4 -c:v libx264 -crf 23 out_h264.mp4
ffmpeg -i test_src.mp4 -c:v libx265 -crf 23 out_h265.mp4
ls -lh out_h264.mp4 out_h265.mp4   # H.265 明显更小
```

### 7.6 看 profile/level

```bash
ffprobe -v error -select_streams v -show_entries stream=profile,level out_h264.mp4
```

## 八、软编 vs 硬编：什么时候用哪个

| 维度 | 软编（x264/x265） | 硬编（VENC/GPU） |
|:---|:---|:---|
| CPU 占用 | 高 | 低 |
| 压缩率 | 更好（算法精细） | 略差（同码率 PSNR 低 0.5~2dB） |
| 延迟 | 高 | 低 |
| 实时性 | 4K30 吃力 | 轻松 |
| 适用 | PC 离线转码 | 嵌入式实时推流 |

**嵌入式结论**：板端实时编码用硬件 VENC；PC 端离线转码/验证用 FFmpeg 软编。**两者参数概念完全一致**（GOP/码率/帧类型），这就是本篇的意义——把概念搞懂，硬编只是换个接口。
