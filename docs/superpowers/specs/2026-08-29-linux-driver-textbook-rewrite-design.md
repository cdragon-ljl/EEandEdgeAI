# Linux 驱动系列教材式重写设计

日期：2026-08-29

状态：设计方向已确认，等待书面规范复核

## 1. 背景

现有 Linux Driver 系列虽然覆盖范围较广，也包含大量代码、表格和 Mermaid 图，但整体阅读体验更接近工程评审材料，而不是面向初学者的教材。

典型问题包括：

- 单篇承担的主题过多。第一篇同时包含内核模块、Kbuild、字符设备、ABI、poll 和卸载；设备模型文章同时展开 kobject、sysfs、devres、PM 与解绑。
- 概念出现速度过快。读者还未通过实验建立直观认识，就进入生命周期、异常回滚和生产级约束。
- 命令式措辞过多。全系列频繁出现“必须”“不能”“验收”等表述，使阅读过程持续处于审查和判断状态。
- 图表与表格密度过高。图表不再只是解释难点，而是在不断切断正文叙述。
- 文章结构趋同。不同主题被套入类似的资源、生命周期、故障矩阵和验收模板，缺少自然的教学节奏。

本次重写不在现有文章上继续润色或扩写，而是重新设计课程粒度和叙述方法。

## 2. 目标

### 2.1 读者

目标读者具备以下基础：

- 掌握 C 语言；
- 能阅读简单 Makefile；
- 会使用常见 Linux 命令；
- 没有系统学习过 Linux 驱动开发。

文章不重复讲解 C 语言基础，也不假定读者理解 VFS、设备模型、设备树、中断上下文或内核同步。

### 2.2 教学目标

读者完成主线后，应能够：

- 理解 Linux 驱动的基本抽象和常见内核对象；
- 独立编译、加载、调试一个外部内核模块；
- 编写字符设备和 platform 驱动；
- 使用设备树描述 RV1126 板级资源；
- 理解 GPIO、中断、I2C、SPI、PWM、IIO、RTC 等常见框架；
- 建立 DMA、IOMMU、显示、存储、USB、TTY、PCIe 和网络子系统的整体认识；
- 使用 Linux 官方调试工具定位驱动问题；
- 在学习完基本原理后，理解错误回滚、解绑、并发与长稳测试等工程要求。

### 2.3 平台与版本

- 通用原理和关键源码以 Linux 6.12 LTS 为主要基线。
- 板级实验以项目现有 RV1126 环境为例。
- RV1126 厂商 SDK 与 Linux 6.12 的差异必须单独标注。
- 不能把厂商 4.19/5.10 内核中的私有接口写成 Linux 通用接口。

## 3. 非目标

- 不追求复刻野火的原文、代码或章节文字。
- 不通过增加行数、标题数、表格数和图表数证明文章详细。
- 不在 Linux Driver 主线中重复完整的 USB、V4L2、ASoC 应用专题。
- 不让生产级异常处理提前打断入门阶段。
- 不把每篇文章写成完全相同的可见模板。

## 4. 教学方法

每篇文章围绕一个主要问题展开，采用以下自然顺序，但不强制使用相同的二级标题：

1. 承接前一篇已经建立的知识；
2. 通过具体硬件或程序现象提出本篇问题；
3. 先给出直观模型，再引入内核术语；
4. 阅读解决当前问题所需的关键数据结构和调用链；
5. 完成一个可以编译、部署和观察的实验；
6. 根据日志、sysfs、设备节点或波形解释实验结果；
7. 总结本篇结论，并说明下一篇为什么自然出现。

高级边界只在正文已经需要时引入。ABI 兼容、复杂回滚、热解绑、长稳和性能门禁集中放在后段工程章节。

## 6. 写作与排版规则

### 6.1 叙述

- 连续解释优先于清单。
- 一个段落应完整表达一个因果关系，不为了视觉长度把一句话拆成多段。
- 新术语首次出现时先解释用途，再给出结构体或 API。
- 中英文术语以中文叙述为主，必要的内核标识符使用反引号。
- 避免反复使用“必须”“不能”“验收”“边界”“闭环”等工程审查措辞。
- 常见错误放在对应知识点附近解释，不统一堆到巨大故障矩阵。

### 6.2 标题

- 正文中已有的二级、三级标题使用可见的层级数字编号：二级标题写作 `## 1. 描述性标题`，三级标题写作 `### 1.1 描述性标题`，三级标题的主编号与所属二级标题一致。
- 数字编号只表达章节层级和阅读位置，不表示“第一步、第二步”式流程模板。
- 标题服务于内容逻辑，不规定每篇固定数量，也不要求文章至少包含一个二级或三级标题。
- 不使用统一的“第一步、第二步、第三步、第四步”模板。
- 不为单段说明创建二级标题。
- 章节层级通常不超过三级。

### 6.3 代码

- 代码围绕当前知识点逐步生长，避免一次贴出完整复杂驱动后再倒推。
- 示例必须说明哪些部分可以直接运行，哪些只是结构示意。
- 内核代码引用标明文件路径、版本基线和省略部分。
- 实验代码包括编译、部署、运行、日志与清理方法。
- RV1126 DTS 属性必须来自现有设备树、binding 或厂商内核，不能编造占位值后伪装成可运行示例。

### 6.4 图表

- 只为对象关系、时序、调用链或数据流绘图。
- 一张图只回答一个问题。
- 简单的先后顺序用正文描述，不强行转换为 Mermaid。
- 图表数量不作为自动质量指标。
- 所有 Mermaid 在发布前使用实际解析器验证。

### 6.5 表格

- 表格只用于真正需要横向比较的数据。
- 连续原理说明不转换为表格。
- 一篇文章不设置固定表格数量。

## 7. 单篇质量检查

单篇完成的判断依据是知识闭环，而不是字数。审阅时检查：

- 开头是否说明了为什么要学习当前主题；
- 是否只依赖前文已经介绍的概念；
- 关键对象和调用链是否解释到足以阅读代码；
- 实验是否能够在指定环境复现；
- 命令输出或硬件现象是否得到解释；
- 是否存在突然出现但未解释的术语；
- 是否有与正文脱节的扩充段落；
- 结尾是否自然衔接下一篇；
- 官方资料和源码引用是否可访问且对应当前结论。

不设置最低行数、最低字数、最低标题数、最低代码块数或最低图表数。

## 8. 内容迁移策略

### 8.1 重写方式

- 30 篇文章按新大纲重新编写，不在当前 28 篇上继续追加“扩展讲解”。
- 当前文章中已验证的代码、官方资料和图可选择性迁移。
- 迁移内容必须重新嵌入新叙事，不能整段复制后形成风格断层。

### 8.2 URL 兼容

- 新文章使用与内容一致的规范 slug。
- 为现有 28 个已发布 slug 建立显式重定向表。
- 仍对应同一主题的旧地址重定向到新文章。
- 已移出主线的 V4L2、ASoC、Remoteproc 等旧页面重定向到对应专题或最接近的扩展入口。
- 自动测试验证每个旧地址都有唯一目标，避免 GitHub Pages 产生 404。

### 8.3 系列框架

- 重写 `linux-driver-framework.md`，只说明学习顺序、阶段目标和先修关系。
- 系列页展示 30 篇文章，不把旧的 28 篇排序继续暴露给读者。
- 每篇文章的上一页/下一页严格跟随新课程顺序。

## 9. 实施策略

### 9.1 样稿

先完成第 1 篇“Linux 驱动开发环境、内核源码与实验方法”。

样稿重点验证：

- 是否具有野火式的顺畅承接和问题驱动叙述；
- 是否避免工程清单语气；
- 是否能让无驱动经验的读者完成环境核对；
- 代码、命令、图表和正文比例是否自然。

样稿经用户确认后，再继续后续文章。

### 9.2 分阶段编写

样稿确认后按课程阶段推进：

1. 第 2～10 篇；
2. 第 11～20 篇；
3. 第 21～28 篇；
4. 第 29～30 篇与全系列统稿。

每个阶段完成后运行结构测试、链接检查和构建，但不要求用户逐篇审批。

### 9.3 全系列统稿

最终统稿检查：

- 前文是否已经解释后文依赖；
- 同一概念的中文译名和内核标识符是否一致；
- 不同文章是否重复大段原理；
- 实验环境和 RV1126 路径是否统一；
- 跨专题链接是否正确；
- 章节结尾与下一篇开头是否连贯。

## 10. 验证

### 10.1 自动验证

- 30 篇 frontmatter、顺序和 slug；
- 野火 38 个目录主题到 30 篇的覆盖映射；
- 28 个历史 slug 的重定向；
- 不存在旧的统一四步模板和“初学者扩展讲解”；
- Markdown/frontmatter 可被 Astro 内容集合加载；
- Mermaid 全量解析；
- 站内链接和官方资料链接检查；
- `npm test`；
- `npx astro check`；
- `npm run build`。

自动测试不检查文章最小长度、最小图表数或最小标题数。

### 10.2 人工验证

- 样稿与野火同类章节进行叙述节奏对照；
- 桌面与移动端阅读检查；
- 连续阅读相邻三篇，检查是否需要反复返回前文；
- 随机选择实验，从空目录开始复现；
- 检查文章是否出现为了显得专业而提前引入的复杂边界。

## 11. 发布

- 样稿阶段只在本地预览，不部署到公开站点。
- 30 篇完成并通过全系列统稿后统一提交。
- 推送 `main` 后等待 GitHub Actions build/deploy 均成功。
- 从公开 GitHub Pages 验证系列页、第 1 篇、阶段切换文章和第 30 篇。
