# Zephyr 实战系列完整性修订设计

## 目标

系统审计并修订 `articles/zephyr` 下的系列总纲和 01-26 篇正文，使每篇文章符合原总纲定义的教学标准：概念首次出现时有定义和迁移类比，关键机制可复现，代码或工程流程形成闭环，API 与配置以 Zephyr 4.4.x 为准。

## 已确认问题

初步审计表明问题不是第 05 篇的个例：

- 系列中的自定义函数普遍缺少职责、参数、返回值和上下文说明。
- 多篇标为完整或可运行的示例缺少入口、对象创建、初始化、配置或错误处理。
- 部分代码存在未定义符号、只展示一半数据链路或声明加载功能却没有注册处理器的问题。
- MCUboot、DFU、板级移植、综合项目和测试文章缺少完成主题所需的文件与验证闭环。
- 系列总纲要求每篇具有可运行代码和 nRF52832 DK 验证路径，当前后半系列没有达到该要求。

## 范围

- 修订 `zephyr-framework.md` 和 `zephyr-01` 至 `zephyr-26`。
- 保留 `03`、`05` 和资源目录中现有未提交改动，在当前工作区内容上增补。
- 不改动其他文章系列。
- 不新增独立示例代码库；完整代码与必要工程文件保留在对应文章中，验证时可抽取到临时目录。
- 不为配置或流程主题强行添加无意义的 `main.c`，但每篇必须提供与主题匹配的可复现闭环。

## 修订批次

全系列按主题分成八个可独立验收的批次：

1. 总纲与工程基础：`zephyr-framework.md`、`01-04`
2. 内核机制：`05-08`
3. 设备与驱动：`09-12`
4. BLE 应用：`13-16`
5. 电源、调试与存储：`17-19`
6. MCUboot 与 DFU：`20-21`
7. 高级外设与板级移植：`22-24`
8. 综合项目与测试：`25-26`

先实施 `05-08`，因为该批已发现确定的线程签名、对象创建和示例闭环问题。每批完成正文审计、官方资料核对、修改、静态检查和可行的构建验证后再进入下一批。

## 统一完整性标准

### 概念与接口

- 概念首次出现时给出准确定义，并在适合时提供 FreeRTOS 或裸机类比。
- 宏按宏说明，函数按函数说明，不混淆二者。
- 重要 Zephyr 接口首次出现时列出准确签名、参数语义、返回值、调用上下文和常见错误。
- 自定义函数使用简洁的 Doxygen 风格注释，覆盖职责、有效参数、返回值和线程或 ISR 限制；无意义的逐行注释不作为完成标准。

### 代码型文章

- 至少包含一个可独立理解的完整应用或完整测试。
- 补齐头文件、常量、类型、全局对象、入口函数、初始化顺序、错误处理和可观察输出。
- 涉及硬件时补齐必要的 devicetree overlay、Kconfig、接线或节点前提。
- 涉及构建时提供最小 `CMakeLists.txt`、`prj.conf` 和目标明确的 `west` 命令，或清楚声明沿用文章中已给出的统一工程骨架。
- 片段代码必须标为片段，说明插入位置、依赖符号和它与完整示例的关系。

### 工程与流程型文章

- 提供完整目录、关键配置文件、命令顺序、产物位置、成功判据和失败排查方法。
- MCUboot 与 DFU 文章必须覆盖构建、签名、分区、测试启动、确认或回滚的实际闭环。
- 板级移植文章必须给出符合 hardware model v2 的最小文件集合及各文件可用内容，不只给目录名。
- 综合项目必须给出关键模块接口和实现，测试文章必须提供可直接由 Twister 发现的完整测试工程。

## 技术核对

每批优先使用 Zephyr 4.4 官方文档、API 文档、官方样例和对应版本源码核对：

- API 签名、参数类型、返回值和 ISR 或线程上下文限制。
- Kconfig 选项及其依赖。
- devicetree binding、节点属性和 hardware model v2 文件结构。
- nRF52 DK 的 Zephyr 4.4 目标名 `nrf52dk/nrf52832`。
- BLE、settings、MCUboot、MCUmgr、Twister 等子系统在 4.4 中的推荐用法。

无法从 4.4 资料确认的内容不写成确定结论；需要硬件才能证明的现象不声称已在板上验证。

## 验证策略

每批执行以下检查：

1. 检查 Markdown 围栏、标题层级、表格、链接和 Mermaid 块闭合。
2. 扫描系列写作红线和过时板级名称。
3. 抽取完整代码块，检查头文件、符号定义、函数签名、配置和文件依赖闭合。
4. 本地存在可用 Zephyr 4.4 环境时，对适用示例构建 `nrf52dk/nrf52832` 或 `native_sim`。
5. 无法实际构建或需要硬件验证时，记录验证边界，不把静态检查写成运行成功。
6. 查看 Git 差异，确认没有覆盖用户已有修改或波及批次外文件。

全部批次完成后，再检查术语、版本、板级名称、示例目录和跨文章引用的一致性。

## 错误处理原则

- 示例不能静默忽略会影响初始化、数据有效性或资源生命周期的错误。
- 日志应指出失败的接口和错误码，但不在 ISR 中执行不适合的日志或阻塞操作。
- 对可以合理恢复的错误给出重试、退避、丢弃或降级策略；不可恢复的初始化失败给出清楚的停止或返回行为。
- 并发示例明确对象所有者、数据生命周期和线程与 ISR 边界。

## 完成标准

- 每篇都通过统一检查表，没有“标题声称完整、正文只给骨架”的情况。
- 读者无需猜测关键接口参数，也不会因未定义符号或缺失配置而无法复现主要示例。
- 每篇的练习和里程碑与正文实际交付的内容一致。
- 全系列保留面向 FreeRTOS 与裸机工程师、以 nRF52832 DK 为主线的定位。
